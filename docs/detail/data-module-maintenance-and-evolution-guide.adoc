== 2. 维护场景快速入口

=== 2.1 新成员 Onboarding（建议顺序）

- 第 1 阶段（10 分钟）：阅读输入清单，建立模块地图。

=== 2.2 线上问题分类

- 启动失败：优先检查依赖与自动配置加载。
- 查询异常：优先检查 `BaseRequest` 参数与查询构建器。
- 写入异常：优先检查 `CrudInterceptor` 链路与实现层保存逻辑。
- 删除语义争议：优先核对 `delete/remove/physicalDelete` 的实现映射。

== 3. 标准排障路径

=== 3.1 启动期排障

1. 确认依赖是否引入了目标 starter（`-mybatis` 或 `-jpa`）。
2. 检查 `AutoConfiguration.imports` 是否声明对应配置类。
3. 检查数据源与 JPA/MyBatis 必需配置是否齐全。

=== 3.2 查询期排障

1. 校验请求对象是否继承 `BaseRequest`。
2. 校验分页参数 `page/size` 是否合理。
3. MyBatis 路线排查 `filedQueries/sorts` 的结构。
4. JPA 路线排查 `Specification` 构建逻辑。

=== 3.3 写入期排障

1. 确认调用了 `add/update/edit/remove/delete` 的哪个语义入口。
2. 检查 `CrudInterceptorExecutor` 是否在 `beforeCheck/before` 阶段拦截。
3. 确认实现层（MyBatis/JPA）是否实际落库并返回预期对象。
4. 如需物理删除，确认是否实现了 `physicalDelete`。

== 5. 常见扩展策略

=== 5.1 新增领域实体（推荐流程）

1. 选择实现路线（MyBatis 或 JPA）。
2. 新建 Entity 与 Query（继承 `BaseRequest`）。
3. 新建 Service（继承对应基类）。
4. 新建 Controller（继承对应 BaseController）。
5. 按最小 CRUD 路径完成验证。

=== 5.2 新增跨实体审计/规则

1. 实现 `IJdbcCrudInterceptor`，声明 `entityType()` 与 `order`。
2. 在 `beforeCheck/before/after/onError` 中实现规则。
3. 用写入链路验证是否按预期触发。

=== 5.3 实现层切换（MyBatis <-> JPA）

1. 保持上层请求与返回模型稳定。
2. 对齐删除语义（`delete/remove`）与 DTO 契约。
3. 对齐查询表达能力（`filedQueries` vs Specification）。

== 7. 残余风险清单

- Mongo 路线仍无完整 CRUD 基础设施，若对外宣称“已支持 Mongo 统一接入”会产生偏差。
- 历史命名拼写（`serivce`、`filedQueries`）仍是当前契约，后续重构需配套兼容策略。
- `delete/remove` 双命名长期并存可能增加调用方误用概率。
